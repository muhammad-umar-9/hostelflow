## Architecture to implement

Use a single full-stack Next.js application on the same origin. Do not create a separate public backend service unless there is a demonstrated need.

Production containers:

- `app`: Next.js standalone production server
- `postgres`: PostgreSQL with a private internal network and persistent volume
- `minio`: S3-compatible private object storage with a private internal network and persistent volume
- `caddy`: the only public entry point; terminates HTTPS and proxies the app
- `backup`: scheduled PostgreSQL and MinIO backup job with retention settings and an external backup destination configuration

Use:

- PostgreSQL as the source of truth
- Prisma for schema, migrations and typed database access
- server actions and/or route handlers for mutations and protected downloads
- Auth.js or Better Auth for secure session authentication; select one based on current official documentation and explain the choice
- Zod validation on the server, even when client validation exists
- MinIO private buckets for CNICs, photographs, payment proofs, police documents, damage evidence and generated PDFs
- Docker Compose for development and production-compatible deployment
- Caddy as a reverse proxy with HTTPS
- Playwright plus unit/integration tests

Keep PostgreSQL and MinIO ports inaccessible from the public internet. Only Caddy should publish ports 80 and 443. Do not expose Prisma Studio in production.

## Integration approach

The current frontend contains:

- `lib/repository/types.ts`
- `lib/repository/mock-repository.ts`
- `lib/repository/index.ts`
- `components/providers/hostel-provider.tsx`

Do not merely replace the repository with an unrestricted browser API that downloads the entire hostel database. Refactor data access by screen and user role:

- Server components should fetch protected data directly on the server where practical.
- Client components may receive only the minimal serialized data they need.
- Mutations must call authenticated server actions/route handlers.
- TanStack Query may be used for interactive queues and filtered client data.
- Never send another resident’s private fields or document keys to a resident session.
- Remove every direct production import from `lib/mock-data`.
- Keep mock repositories only for tests, Storybook/demo fixtures or development mode, clearly isolated from production.

Replace the global `HostelData` snapshot pattern. It is unsuitable for a real multi-user system because it loads too much information, risks stale writes and cannot safely authorize at record level.

## Security requirements

- HTTPS only in production
- secure HTTP-only same-site cookies
- rate-limited login and upload routes
- CSRF protection where relevant
- strict server-side tenant and role authorization
- private document objects and short-lived access
- MIME and file-signature validation
- upload size limits
- randomized storage keys without CNIC in paths
- CNIC masking in lists and logs
- encrypted backups or protected backup destination
- no secrets in client bundles or `NEXT_PUBLIC_*` variables
- no raw signed URLs in logs
- verified payments corrected only through reversal/adjustment records
- deposit stored as a ledger
- audit records for document access and financial changes
- database constraints plus transactions for allocation and payments
